# 設計書（1週目版）

> 状態：下書き。Day1で、自分の目で見直して、必要なら直す。直した点は `docs/learning-log.md` に残す。

## 1. 背景と目的
- 前職（税理士事務所）では、顧客ごとの決算・年末調整・支払調書・償却資産・納期特例などの進捗を、
  約300列の横長Excelで管理していた。列が増えるほど見づらく、期限が近い作業を探しにくかった
- 1週間で「案件（作業の1件）」を管理するWebアプリを作る。2週目以降で、顧客・担当者・作業の種類を別テーブルに分け、
  正しく正規化する

## 2. 1週目のスコープ
- やる：案件の登録・一覧・更新・削除。一覧の絞り込み（ステータス・担当者）と期限順の並び替え。期限による区切り表示と期限切れの強調表示
- やらない：ログイン、顧客・担当者のマスタ、作業ステップの管理、請求・訪問の記録

## 3. 案件の項目

| 顧客名 | サンプル商事 | ○ |
| 作業の種類 | 決算申告 | ○ |
| 期限 | 2026-11-30 | ○ |
| 担当者 | 担当A | |
| ステータス | 作業中 | ○ |

作業の種類（この6つから選ぶ。表記を統一する）：決算申告／予定申告／年末調整／支払調書／償却資産／納期特例
ステータス（共通の5つ。Javaのenumで持つ）：未着手／資料待ち／作業中／確認待ち／完了

## 5. API一覧
| やること | メソッド | URL | 備考 |
|---|---|---|---|
| 一覧を取る | GET | /api/cases | 絞り込み条件つき（下記）。期限の昇順 |
| 1件を取る | GET | /api/cases/{id} | 編集画面用 |
| 登録する | POST | /api/cases | 入力チェックあり |
| 更新する | PUT | /api/cases/{id} | 入力チェックあり |
| 削除する | DELETE | /api/cases/{id} | |

一覧の絞り込み（すべて任意）：`status=IN_PROGRESS`、`assignee=担当A`
期限による区切りは、APIでは行わない。期限順に取ってきた一覧を、画面（Vue）の側で区切る
存在しないid（削除済みなど）を取得・更新・削除しようとしたときは、404（見つかりません）を返す。画面には「この案件はすでに削除されています」と出す

## 6. 画面
手描きの画面：`docs/screens/list.jpg`、`docs/screens/form.jpg`

1. **一覧画面**：案件の表（顧客名・担当者・作業の種類・ステータス・期限）。上に絞り込み欄（担当者・ステータス）と「新規登録」ボタン。
   表は期限で「期限切れ／今週／今月／来月以降」の4つに区切る。期限切れ（期限が過ぎて未完了）は赤字にして、一番上に出す。
   完了した案件も、期限に合わせて同じ区切りに表示する（ステータス列で見分ける）。期限が過ぎた完了案件は、普段は一覧に出さず、ステータスで「完了」を選んだときだけ表示する。
   区切りの定義（どの案件も、ちょうど1つに入る）：期限切れ＝今日より前／今週＝今日〜今週の日曜（週は月曜始まり）／今月＝今週の日曜の翌日〜今月末／来月以降＝それより後
   行を押すと、右側に編集パネルが開く
2. **登録・編集パネル**（一覧の右に表示）：顧客名・作業の種類（選択）・期限（日付）・担当者・ステータス（選択）・メモ。
   「保存」「キャンセル」。編集のときだけ「削除」ボタン（確認つき）を出す。顧客名は編集でも変更できる

## 7. 入力チェック
- 顧客名・作業の種類・期限・ステータスは必須。顧客名は100文字以内。メモは500文字以内
- 作業の種類は、決まった6つ以外を受け付けない

## 8. 将来像（2週目以降）
```
顧客 ──< 案件 >── 作業の種類 ──< 作業ステップ(マスタ)
            └──< 案件ステップ（各ステップの進み具合）
担当者(マスタ) ──< 案件 / 顧客の担当履歴（開始日・終了日）
```
- 顧客・担当者・作業の種類を別テーブルにして、FKで連携する
- 担当者マスタは退職者を削除せず、フラグで論理削除する。顧客の担当は履歴（開始日・終了日）を持つ
- 作業ステップのマスタ（例：決算申告＝資料収受→会計入力→締め・チェック→申告書作成→内部チェック→顧客承認→申告手続き→納書渡し→決算後処理）
- 案件の自動作成（顧客の決算月から、今期の決算案件を一括作成）
- 登録忘れの防止、Flywayなどによるテーブル変更の管理

### Day1の見直しで気づいたこと（1週目には入れない）
- 作業ごとの日付（資料収受日・申告日など）が必要 → 「案件ステップ」に各ステップの完了日を持たせる
- 作業の種類ごとに、ステップ（資料収受→入力→確認待ち…）の中身が違う → 「作業ステップ（マスタ）」で作業の種類ごとに定義する
- 次年度に使う税の情報（課税売上など）が必要 → 案件ではなく顧客の情報なので、「顧客マスタ」に持たせる
- 顧客名を文字で入れると表記ゆれ（例：サンプル商事／㈱サンプル商事）で重複する → 顧客マスタから選ぶ形にする
- 「誰が・いつ・何を変えたか」を遡れるようにしたい → ログインと `updated_by` 列、さらに変更履歴テーブルを作る（`updated_at` は最後の更新日時しか残らない）
- 2人が同じ案件を同時に編集すると、後から保存した内容で上書きされる → `version` 列による楽観的ロックで、保存時にぶつかりを検出する

### Day3で気づいたこと（1週目には入れない）
- 1週目の削除は物理削除（行を消す）。間違えて消したときに戻せない・後から調べられない → `deleted_at` 列による論理削除を検討する（一覧・取得・更新のすべてで、削除済みを除く条件が必要になる）
